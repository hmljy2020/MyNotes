# 从 SSA 和活跃性分析理解固定架构寄存器分配

日期：2026-11-14

## 遇到的问题

我在讨论 PTO trace 如何接入 tile 粒度性能模型时，想弄清楚：负载已经记录了 tile 的生产者和消费者，为什么还需要考虑编译器生命周期分析、寄存器命名和硬件动态分配？

看 C++ tile 算子时，我注意到同一个 `tA`、`tC` 可以反复作为操作的输入和输出。我最初没有分清变量名、每次计算产生的值，以及实际保存这些值的寄存器。于是先退回普通 CPU 程序，理解它如何使用一组固定的架构寄存器名字，再继续研究“滑动架构寄存器”。

这里的“固定”指指令引用 `r1`、`r2` 这类固定的架构名字，并不意味着运行时始终使用同一个物理存储位置。

## 学到的解决方法与知识

### 先区分类型、变量和每次定义的值

`tileA tA;` 类比 `int x;`：`tileA` 是类型，`tA` 是变量。后续操作反复写入 `tA`，产生的是这个变量的不同值，不是反复声明新的 C++ 对象。

声明确定变量及其类型约束；仅凭 tile 变量声明，不能断定已经占用了硬件 TileReg，或者其中的数据已经有效。

### SSA 先把值的关系讲清楚

下面用伪代码表示一段直线程序：

```text
a = load(p)
b = a + 1
a = b * 2
store(q, a)
```

将不同定义区分为 SSA 值后，可以理解成：

```text
a0 = load(p)
b0 = a0 + 1
a1 = b0 * 2
store(q, a1)
```

我的收获是：变量名反复使用容易让人混淆，而值的版本把“谁产生、谁使用”直接说明白了。编译器可以据此优化，例如传播常量、消除无用计算。

SSA 的“一次定义”针对静态程序。同一条循环体指令可以执行多次；展开的动态 trace 还可以进一步区分各次迭代产生的值。分支合流和循环中的值选择需要额外表示，例如 SSA 的 φ 节点。[LLVM SSA 与 φ 语义](https://llvm.org/docs/LangRef.html#phi-instruction)

这是一条理解编译过程的主线，不要求所有编译器都把源码中的每次赋值机械地变成一个最终保留的 SSA 值。实际还会经历优化、指令选择以及 SSA 消解。

### 给每个值新编号，首先解决的是命名

我最初想到的分配方法是：每产生一个值，就给它一个新的寄存器编号。

在虚拟寄存器层面可以这样理解，因为它的编号数量不受硬件寄存器数量直接限制。但真实目标只有有限的架构寄存器，不能把所有新编号原样塞进机器指令。

因此，编译器还要把虚拟寄存器安排到有限的目标寄存器中，必要时将部分值放到栈上，插入保存和重新加载，也就是 spill。[LLVM 寄存器分配说明](https://llvm.org/docs/CodeGenerator.html#register-allocation)

### 活跃性分析决定何时能够复用

我之前笼统称它为“生命周期分析”，更准确的名称是活跃性分析（liveness analysis）。它关心：在程序的某个位置，这个值后面是否还可能被使用？

对于上面的直线程序：

| 值 | 产生位置 | 最后一次使用 |
|---|---|---|
| `a0` | load | 加法 |
| `b0` | 加法 | 乘法 |
| `a1` | 乘法 | store |

如果指令允许目的寄存器与源寄存器相同，就可以安排成下面的示意汇编：

```asm
LOAD  r1, [p]       ; r1 保存 a0
ADD   r1, r1, 1     ; 读 a0 后，r1 保存 b0
MUL   r1, r1, 2     ; 读 b0 后，r1 保存 a1
STORE [q], r1
```

三个值都保留下来了，但可以先后使用同一个 `r1`。这不是把三个值合并成一个值，而是复用保存位置。以上例子用于说明原理，没有实际编译验证，也不表示优化器一定生成这组指令。

我现在抓住的规则是：**一个值后续不再需要时，编译器就可以把原来分配给它的寄存器安排给其他值。**如果两个不同的值需要同时保留，通常就需要不同位置。

实际分配还受寄存器类别、指令限制、调用约定等约束。存在分支和循环时，需要考虑控制流，不能把源码最后出现的位置直接当作生命周期结束。活跃性分析提供依据，寄存器分配再决定编号、复用及 spill。[LLVM 活跃区间分析](https://llvm.org/docs/CodeGenerator.html#live-intervals)

### 编译器分配与硬件重命名是两层事情

我用下面这条链区分它们：

```text
源码变量
  → SSA 值及后续机器虚拟寄存器
  → 编译器安排架构寄存器
  → 乱序硬件运行时重命名到物理寄存器
```

前面连续写 `r1` 的指令，在带物理寄存器重命名的 CPU 上，可以分别获得不同的物理版本。消费者读取对应生产者的版本，这让不同指令有机会在流水线里重叠。

所以，“编译器认为旧值不再活跃，可以复用架构寄存器”和“硬件现在可以回收旧物理寄存器”不是同一件事。后者还要满足具体硬件的安全回收条件，常与退休、恢复机制有关。

还有一个术语容易混淆：LLVM 后端文档也把虚拟寄存器分配到的目标寄存器称为 physical register。这里的目标寄存器名字，例如 `EAX`，和乱序微架构内部的 PRF 槽位不是同一个层次。[LLVM 寄存器表示](https://llvm.org/docs/CodeGenerator.html#how-registers-are-represented-in-llvm)

## 回到 PTO trace 的理解

我现在可以更准确地理解现有 trace：它用版本和输入输出关系，直接告诉模型某次执行中谁产生了哪个 tile、谁会消费它。这些信息可以作为活跃性和最后一次使用分析的基础。

但它没有因此自动确定物理 TileReg 的分配和释放。分析知道“未来还有哪些使用者”，模型还要决定“什么时候占容量、什么时候 ready、满足什么条件才能回收”。尤其不能因为源码变量名相同，就直接认定不同值版本必须覆盖同一个物理位置。

## 下一步：理解滑动架构寄存器

这次先建立了固定架构寄存器的心智模型。接下来我还需要理解 SSM 所采用的相对命名、环形 vtag 等机制，与这里的寄存器分配有何联系。

准备继续追问：

1. 为什么要引入“滑动”的命名方式？它希望减少哪些编译器或硬件工作？
2. 消费者引用的是固定名字，还是相对于某个定义位置的距离？窗口何时推进？
3. 活跃性分析、长期复用和最后一次使用信息，在这种方式下如何表达？
4. 架构命名窗口、环形 vtag 表项和物理 ptag 空间，各自在什么时候分配、回收？
5. 输入已经是带动态版本的 PTO trace 时，哪些命名过程可以简化，哪些容量和生命周期约束仍要保留？

这些是下一阶段的问题，目前还没有形成结论；“滑动”也需要结合具体 ISA 定义，不能直接与旋转寄存器或其他窗口机制画等号。
