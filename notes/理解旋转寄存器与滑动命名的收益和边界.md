# 理解旋转寄存器与滑动命名的收益和边界

日期：2026-11-14

## 遇到的问题

在理解了 [SSA、活跃性分析和固定架构寄存器分配](从SSA和活跃性分析理解固定架构寄存器分配.md)之后，我继续研究 PTO 的 tile 相对命名，希望弄清楚它给编译器和硬件带来的实际收益。

PTO Local 用 T/U/M/N 四路命名，每路可以引用最近的 16 个位置。我起初听到的解释是：这种方式有利于流水、简化重命名、让指令更紧凑。但仔细想，消费者仍然需要从 64 个位置中选一个；不同值仍要占物理空间；指令也仍要知道自己读取哪个版本。那么究竟省掉了什么？

这次我把问题拆成编码、名字映射和循环流水三部分，逐一比较。下面的代码都是说明原理的伪代码，没有经过编译或性能测试，也不是完整的 PTO 汇编。

## 学到的解决方法与知识

### 先区分旋转寄存器与 PTO 的滑动命名

“旋转寄存器”（rotating registers）是标准术语。例如 Itanium 在特定的软件流水循环分支处更新旋转基址，让同一个值通过另一个寄存器名字被引用。它可以帮助不同循环迭代的数据共存。[Intel 手册 §5.4.1](https://www.intel.com/content/dam/www/public/us/en/documents/manuals/itanium-architecture-software-developer-rev-2-3-vol-1-manual.pdf)

PTO Local 更适合称为相对命名或滑动命名：向某一路发布新结果时，新结果成为该路的 `#1`，旧结果的相对编号向后移动。它按结果发布推进，与经典的按循环迭代旋转并不完全相同。[PTO Local 规范，版本 b0165320](https://github.com/PTO-ISA/pto-spec/blob/b0165320a4b575b18d2f4d93faf40178f661ab49/asl/tile/model/state/local-registers.asl)

```text
产生 A → T：T#1 指向 A
产生 B → T：T#1 指向 B，T#2 指向 A
```

我的理解是：变化的是名字与值之间的对应关系，数据本身不用跟着移动。两种机制可以放在一起理解，但不能把某种架构的全部收益直接套到另一种架构。

### 编码收益主要在目的端

四路、每路 16 个位置，共有 64 个可引用的逻辑位置。消费者要准确选择其中一个，仍然需要 6 位命名信息。

| 命名字段 | 64 个固定名字 | PTO 四路相对命名 |
|---|---:|---:|
| 源名字 | 6 位 | 6 位：2 位选一路，4 位选相对位置 |
| 目的名字 | 6 位 | 2 位：选一路，新结果隐式成为该路的 `#1` |

所以我确认的是：**每个目的名字可以少表达 4 位信息，源名字并没有因此更省。**这里仅比较命名字段，不包含大小、参与 PE 等其他字段；整条指令是否变短还取决于编码布局。目的发布与源引用规则见 [B.IOT 规范](https://github.com/PTO-ISA/pto-spec/blob/b0165320a4b575b18d2f4d93faf40178f661ab49/asl/block/operands/B.IOT.asl)。

### 滑动命名没有自动减少映射表项

在“一份表项记录一个可引用位置的映射”这个抽象下：

```text
固定命名：map[64]       → 64 个映射表项
滑动命名：map[4][16]    → 仍然是 64 个映射表项
```

每一路可以用环形映射队列实现，额外维护一个头指针。若头指针指向最新位置，并约定向后存放旧映射，查询可以写成：

```text
map[hand][(head + x - 1) % 16]    # 查询 hand#x
```

这是可能的实现方式，不是对 SSM 内部数据结构的逐项复述。表项可以直接记录 ptag，也可以先指向稳定版本再间接查找物理存储。

变化主要是更新规则：固定命名更新指令指定的表项；滑动命名向指定队列追加映射。后者更规则，但前者的指定表项写入本身也不复杂，不能仅凭这一点断言硬件更小、更快。

### 已进入执行流程的指令，仍然必须绑定稳定版本

固定命名的例子：

```text
生产 A → r0     分配 p7，映射 r0 → p7
消费 r0        绑定 p7
生产 B → r0     分配 p9，映射 r0 → p9
```

滑动命名的例子：

```text
生产 A → T      分配 p7，映射 T#1 → p7
消费 T#1       绑定 p7
生产 B → T      分配 p9，映射 T#1 → p9，T#2 → p7
```

两种情况下，已经绑定的消费者都必须继续读取 A，不能因为名字映射随后变化而改读 B。稳定绑定可以使用物理标签或带代际的版本身份，不要求一定直接保存一个裸 ptag。

因此，对动态分配、乱序执行的 tile 模型，物理分配、源版本绑定、就绪判断和安全释放仍然存在。**“使用滑动命名，所以不需要重命名管理”这个说法不成立。**

经典旋转寄存器可以依靠基址和偏移完成规则映射，由编译器保证复用安全；这与从空闲池为每个结果动态分配物理位置，是不同的责任划分。Mill 的 belt 设计也强调单赋值与减少传统重命名开销，但这是它的整套架构设计，不能直接作为 SSM 简化幅度的证据。[Mill：The Belt](https://millcomputing.com/docs/belt/)

### 循环流水的收益：相同指令可以引用不同轮次的数据

我用一个规则数据流理解这件事：每轮加载一个 A，同时计算两轮前加载的 A。

| 流水轮次 | 加载 | 计算 |
|---|---|---|
| 0 | A₀ | 暂无 |
| 1 | A₁ | 暂无 |
| 2 | A₂ | A₀ |
| 3 | A₃ | A₁ |
| 4 | A₄ | A₂ |
| 5 | A₅ | A₃ |

按照先加载、再引用旧值的顺序，使用三个固定名字保存这些版本，稳定阶段可以安排成：

```text
第 2 轮：LOAD A₂ → r2；COMPUTE r0
第 3 轮：LOAD A₃ → r0；COMPUTE r1
第 4 轮：LOAD A₄ → r1；COMPUTE r2
第 5 轮：LOAD A₅ → r2；COMPUTE r0
```

每轮的操作相同，寄存器编号却不同。普通指令通常不能把寄存器编号写成运行时表达式 `r[轮次 % 3]`，所以一种实现方法是展开三轮，让编号组合循环重复。

使用相对命名，假设每轮只向 T 加入一个结果，计算也不向 T 发布结果，那么每次加载之后都有：

```text
T#1 = 本轮加载的 A
T#2 = 上轮加载的 A
T#3 = 两轮前加载的 A
```

稳定阶段便可反复执行相同的指令：

```text
loop:
    LOAD A[k] → T
    COMPUTE T#3
    k = k + 1
    跳回 loop
```

这里省略地址更新细节、流水启动与收尾、容量及执行就绪检查；“轮次”也不等于硬件周期。对 PTO 来说，这里是两条先后绑定的操作，不能把它们合成一条指令后仍按相同的 `#3` 理解，因为同一操作的源在目的分配前解析。

我现在理解的收益是：**相对名字把“固定延后几轮消费”的关系直接写进操作数，同一段代码就能反复引用不同迭代的值。**经典旋转寄存器也能支持紧凑的软件流水，减少为寄存器轮换而进行的循环展开；某些方案还可以避免额外复制。[Intel 手册 §5.3.2—§5.4](https://www.intel.com/content/dam/www/public/us/en/documents/manuals/itanium-architecture-software-developer-rev-2-3-vol-1-manual.pdf)

普通乱序 CPU 的动态重命名能保护已经绑定的旧值，但后来的 `r0` 读取仍然对应最近的前序 `r0` 写入。它不会自动把这个读取解释成“两次写入之前的版本”。这也是显式相对引用与普通动态重命名的区别。

### 消费者隔得更久，存储需求依然增加

如果每轮都生产一个值，固定延后 7 轮消费，那么加载之后可以用 `T#8` 引用目标版本。指令形式仍然不变，但这时需要容纳更多同时存活的值。

| 数量 | 固定命名 | 滑动命名 |
|---|---|---|
| 同时存活的值及对应存储需求 | 随消费延后增加 | 同样增加 |
| 为轮换名字而需要的不同指令形式 | 可能增加 | 规则数据流下可以保持不变 |

因此，滑动命名节省的是表达轮换的代码，不是保存版本的物理空间。PTO 每路还受 16 个可引用位置限制，超过窗口需要编译器额外处理。窗口推进统计的是该路的新结果，不是经过了多少周期。

## 我对编译器和仿真的理解

编译器仍然需要活跃性分析和调度。固定命名要安排名字分配与复用；相对命名还要计算定义到使用之间推进了多少次、引用是否超出窗口。插入一个同路结果，就可能改变后续引用距离；分支、长生命周期值和不规则循环也需要专门处理。

对我们的静态 tile trace，若已经解析成稳定版本，且两种命名产生相同的依赖、存储约束和执行指令，仅改变名字写法不应产生周期收益。要评估实际优势，需要具体观察是否减少代码展开、复制指令或前端成本，或者证明映射硬件的成本发生了变化。

这次形成的是机制层面的理解。目的命名的信息量和规则流水示例可以直接推导；具体 SSM 的面积、功耗、编译复杂度及周期收益，还没有通过实现对比验证。
