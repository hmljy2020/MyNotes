# 从 CommUnit 设计理解通信协议与 AXI 和 CHI

日期：2026-11-13

## 遇到的问题

我在设计 WSE 与 SSNPU 的联合性能模型，希望核模型执行 tile 指令，把跨核通信交给独立的 CommUnit。核模型提交请求后继续计算，等通信结果可用时再消费结果；CommUnit 负责接收准备、参与节点对齐和 Calendar NoC 上的传输。

最初的问题是数据从哪里发出、接收后落在哪里。继续讨论后，我发现更关键的是：接收方的空间由谁准备？发送方如何知道接收方已经准备好？数据到达是否就能使用？源 tile 又什么时候可以释放？

这些问题使我意识到，通信接口需要约定双方的行为和责任。我想借这个具体设计理解通信协议的必要性，以及它与 MPI、AXI、CHI 等已有机制的联系。

## 学到的解决方法与知识

### 协议需要约定格式和状态变化

我的理解是，一份可用的通信协议至少需要回答以下问题：

| 问题 | 在当前设计中的具体含义 |
|---|---|
| 谁在和谁通信 | 参与节点、通信组、每个节点的通信 owner |
| 这是哪一次通信 | launch、轮次、操作类型，以及本地请求 token |
| 数据是什么 | 源和目的 tile 版本、范围、布局、分片 |
| 什么时候允许传输 | 源数据就绪、接收空间和必要服务已准备 |
| 资源不足怎么办 | 提交背压、等待资源、诊断无法继续的依赖 |
| 什么时候完成 | 本地发送责任收束，接收数据完整且可见 |
| 什么时候可以复用 | 通信及其他消费者都结束了对相关资源的访问 |

本地 token 用于关联请求和完成反馈；跨节点匹配还需要通信组、轮次等共同身份。不同核的本地 token 不必相同。循环重复使用同一个 tile 名称时，还需要区分动态版本，避免旧响应写入已经复用的存储槽。

### 当前方案让各参与核先提交，再由 CommUnit 协调

我准备采用的接口是：各参与核执行逻辑上的 `COMM.SUBMIT`，得到完成 token；后续通过 `COMM.WAIT` 或依赖关系等待结果。它们目前是模型接口的表达，具体机器指令编码仍待确定。

对 AllGather，每个节点的一次提交可以同时描述本节点的发送源和接收目标。核内多个 PE 的准备状态可以先汇总，由一个通信 owner 代表该节点提交。

流程分为以下几个阶段：

1. 核指定源 tile、目标容量和布局，以及本轮通信身份。
2. CommUnit 协同 TileReg 管理逻辑保留源版本，预留目标 backing，登记合法接收范围和预期数据。
3. 必要的发送与接收资源准备完成后，节点参加 align。
4. 参与节点就绪后，按照 Calendar 配置传输。
5. 接收端确认覆盖完整、写入可见，再由 TileReg 管理逻辑发布目标版本就绪。
6. CommUnit 在本地收发义务都满足后返回成功完成。

程序指定逻辑对象和容量，硬件或模型内部完成物理分配。分配可以发生在处理 `SUBMIT` 的过程中，关键是必须在 align 放行之前准备好。

晚到的参与者会使本轮等待。若某个成员始终没有提交匹配请求，这轮通信就无法按当前合同完成；模型应报告缺失参与者或无法推进的状态。不能把正常的晚到直接判成协议错误。

这些是目前准备实现的模型边界，来源于 [CommUnit 接口讨论](https://github.com/hmljy2020/ssnpu-model/issues/2)，还需要通过实现验证容量限制和推进逻辑。

### TileReg 可以成为通信端点，但需要管理异步访问

按照目前的 [WSE 白皮书设计](https://github.com/PTO-ISA/wse-model/blob/e9ecb1aeb766372110bc4d4847f19d4a451c1108/docs/design/wse-system-architecture-whitepaper.md)，发送可通过 MEM/TLSU 获取合法源数据；接收基线路径是经受控写端口写入 Shared backing。Shared Tile 是核内对象，并不意味着不同核天然共享同一份存储。

我需要在 TileReg 管理中补充两类责任：

- **源端保留引用**：异步通信仍可能读取源版本时，保持其绑定有效。可靠复制到发送缓冲后可以结束对应读引用，其他消费者的引用独立管理。
- **目标端接收与发布**：预留目标版本，检查写入授权、代际和范围，等待所有必要写入可见后再发布 ready。

因此，一次片段写入完成不能直接把整个 tile 标为 ready。CommUnit 提供完整性证据，TileReg 管理逻辑负责最终发布；router 本身不直接修改 tile 的就绪状态。

### 用四核 AllGather 理解接收准备

假设四个核各提供 4 KiB 数据，每个核最终需要按 rank 顺序得到 16 KiB 结果。这是一个说明协议的例子，实际接收 arena 可以由多个合法 Shared 对象组成。

| 每个核需要准备的内容 | 大小或含义 |
|---|---|
| 本地发送源 | 4 KiB，通信读引用期间保持有效 |
| 接收结果空间 | 16 KiB，包含四个 rank 的数据 |
| 远端有效数据 | 12 KiB，来自其余三个核 |
| 本地结果分片 | 4 KiB，若网络不提供自投递，则由本地复制补齐 |

远端计量 `expVal` 在这个例子中是 12 KiB。本地复制需要真正完成并可见，但不计入远端字节计量。重复到达的片段也不能重复计数。

结果可用需要同时满足：远端唯一有效数据达到预期、全部目标范围覆盖完整、本地分片完成、写入可见，以及没有故障。只判断“累计字节数够了”会漏掉重复、缺口和尚未完成的存储写入。

Calendar 对准备状态还有时间上的要求：align 表示能够按约定时序收发。缓冲容量足够并不能独自保证及时供数或落地，TLSU、Shared 写端口和跨时钟路径还需要有界服务。这些约束需要进入后续性能模型与调度验证。

### 与成熟通信机制相似在哪里

我可以分别借鉴编程接口和数据传输机制，而不把它们当成同一层协议。

**MPI 非阻塞集合通信提供了接口上的参照。** 发起操作返回 request，程序可以继续做独立工作，再等待完成。同一 communicator 内的参与进程需要按相同顺序调用集合操作；本地完成不等于其他进程也已完成。MPI 本身并不普遍要求所有参与者准备完成后才能开始任何数据传输，我们的 Calendar align 是额外的调度约束。[MPI 4.1 非阻塞集合通信](https://www.mpi-forum.org/docs/mpi-4.1/mpi41-report/node145.htm)

**Rendezvous 提供了接收缓冲准备上的参照。** Linux 内核的 tag matching 文档描述了一种实现：发送方先发送匹配头，可能附带部分数据；匹配接收缓冲登记后，再进行主体数据传输。与之相比，eager 路径可以先发送消息，由系统承担提前到达数据的缓冲责任。我从这里理解到，接收方尚未准备好时，协议必须明确由谁等待、由谁提供额外存储。[Linux tag matching 文档](https://www.kernel.org/doc/html/latest/infiniband/tag_matching.html)

因此，当前方案可以理解为非阻塞集合通信的使用方式，加上接收资源准入和 Calendar 时序约束。具体缓冲登记、握手和搬运仍由模型内部实现。

### AXI 和 CHI 与这里的协议有什么区别

AXI、CHI 和 CommUnit 都规定请求、数据、资源控制和完成条件，但它们管理的操作不同。这里以常见 AXI4 内存映射接口为例。

| 对比项 | AXI4 | CHI | 当前 CommUnit 方案 |
|---|---|---|---|
| 主要操作 | 对地址进行读写 | 内存访问及缓存一致性事务 | 跨核 tile 传输与集合通信 |
| 主要对象 | 地址和突发数据 | 地址、缓存行及一致性状态 | tile 版本、分片和通信轮次 |
| 流控例子 | 通道 VALID/READY 握手 | 链路 credit、事务资源控制 | 请求背压、接收预留和 align |
| 完成范围 | 相应读写事务 | 相应访问及一致性义务 | 本节点本轮收发义务 |

AXI4 有独立的读地址、读数据、写地址、写数据、写响应通道。地址通道握手表示该请求被接收，数据通道握手表示相应数据拍被接收，写响应再反馈写事务结果。普通内存写入由目标控制器服务，目标侧 CPU 不需要为每次写入执行一条匹配接收指令。[Arm AXI4 入门](https://developer.arm.com/-/media/Arm%20Developer%20Community/PDF/Learn%20the%20Architecture/102202_0100_01_Introduction_to_AMBA_AXI.pdf)

CHI 使用请求、响应、数据和侦听等消息，并协调缓存行的状态与访问权限。它的链路 credit 表示接收相应 flit 的资源可用，不能据此推导整个 AllGather 的目标空间已经准备完成。缓存一致性负责协调同一地址的缓存副本；我们的 tile 版本与生命周期管理负责显式对象的就绪、访问和复用，两者的职责不同。[Arm CHI 入门](https://documentation-service.arm.com/static/68590853961937560be90eb2)

这些协议可以组合使用。例如，CommUnit 完成接收准备后，通过某种底层存储接口执行多次写入，再汇总结果、发布 tile。底层可以采用 AXI 类接口或专用接口；一次底层写事务成功只是整轮通信完成的一个条件。

我现在会特别区分三种“准备好”：接口能接收一条消息、组件能接管一项事务、节点具备本轮集合通信的全部必要资源。它们对应不同范围的承诺。

### 对模型设计的实际收获

我准备在模型中显式区分以下事件，让各模块通过消息协作：

| 事件 | 表示什么 |
|---|---|
| 请求接受 | CommUnit 接管描述符，后续负责推进或报告故障 |
| 资源准备完成 | 接收登记、源绑定和必要服务已经满足准入条件 |
| 数据片段写入完成 | 某段数据已经按合同写入并可见 |
| tile 发布 | 该版本满足完整性和其他生产者义务，消费者可以读取 |
| 通信完成 | 本地发送责任收束、接收结果可用，且无故障 |
| 资源释放 | 对象已没有需要保留它的通信责任和其他引用 |

这些事件有依赖关系，但不必都发生在同一时刻。例如源数据可靠进入发送缓冲后，对源 tile 的通信读引用可能先结束，而接收结果尚未完整。

本节点完成也不能代替全网排空。复用通信轮次标识、切换 launch 或重新安装 Calendar 配置，需要另外确认在途传输、待写数据和完成反馈都已收束。出现故障时，同样要隔离失败版本，并等可能访问它的请求终结后再回收空间。

对我而言，协议的价值就在于把这些承诺写清楚：核模型知道何时可以继续计算，TileReg 知道何时可以发布和回收，CommUnit 知道需要等待哪些条件。这样模块可以分别实现，性能模型中的容量、带宽和延迟也都有明确的作用位置。
