# 为什么 PTO 动态版本 trace 可以用于 Local tile 生命周期与调度仿真

日期：2026-11-14

## 遇到的问题

我在研究如何用 PTO trace 驱动 tile 粒度的 SSM 仿真。理解了[固定架构寄存器分配](从SSA和活跃性分析理解固定架构寄存器分配.md)和[滑动命名](理解旋转寄存器与滑动命名的收益和边界.md)之后，我仍然担心：trace 直接使用变量和版本，没有经过真实汇编的寄存器分配与重命名，会不会遗漏 tile 的产生、消费和释放，使调度仿真从输入层面就失真？

这次最重要的收获是：同名变量的多次写入没有在 trace 中混成一个值。每个动态结果都有独立身份，因此可以把它与 SSM 中相应的 Local tile 结果对应起来，再由后端管理实际资源。

我最初把这个结论说成“trace 忠实记录了每个物理 tile 的生命周期，所以仿真是安全的”。这个说法需要收紧：trace 记录的是逻辑结果版本和消费关系；物理分配与释放时刻需要后端模拟。它提供了建立严格对应的基础，并不意味着当前实现已经与 SSM 严格一致。

## 学到的解决方法与知识

### 同名变量不等于同一个动态值

下面是概念示意，不是实际汇编或完整 trace 格式：

```text
op0：产生 B@1
op1：消费 B@1
op2：产生 B@2
op3：消费 B@2
op4：产生 B@3
```

即使源码反复给 `tB` 赋值，trace 也能区分这些结果。口头上说“名称 + version”，当前实现实际使用 `storage_id + version` 标识普通存储版本；循环中新创建的对象也可能获得不同的 storage_id。

消费者明确引用哪个版本，所以它不会因为后面又写了 `tB`，就误读新值。这已经表达了重命名需要保留的关键数据依赖关系。

### 一个动态结果，可以对应一次普通 Local tile 分配生命周期

在操作序列已经对齐、采用普通 Local 数据结果分配路径的前提下，可以建立如下对应：

```text
trace 的一个动态输出版本
    ↔ SSM 中对应操作的一次结果定义
    ↔ 后端中从分配到释放的一条生命周期记录
```

SSM 的普通 eager 路径会为目的 tile 申请映射表项与物理空间。我们可以直接用 trace 版本作为稳定身份，省略从架构相对名字到具体版本的查找过程。这个行为已对照 `RenameSingleTileDst` 和 `SharedTileStatus::Allocate`。[SSM 源码，修订 637bde0](https://github.com/LinxISA/SuperScalarModel/blob/637bde0ec63955c4796828b297e16a057efad3cc/TimingSim/frontend/bctrl/BIssue.cpp)

这里对应的是一次分配生命周期，而不是永久绑定一个物理地址。B@1 释放后，B@3 可以复用它原来占用的空间；三次结果定义也不意味着峰值一定同时占用三份空间。

普通支持重命名的乱序 CPU 也有类似关系：连续三次写同一个架构寄存器，可以产生三个物理版本。这让我意识到，稳定的动态值身份并不是滑动命名独有的。架构命名决定程序如何引用值，物理分配决定这些值如何占用资源。

### trace 保留消费关系，后端实现物理生命周期

我现在用下面的分工理解模型：

| 环节 | trace 提供的信息 | 后端需要实施的规则 |
|---|---|---|
| 分配 | 输出版本、大小和所属存储层级 | 分配时机、顺序、容量与资源不足时的阻塞 |
| 生产 | 产生版本的操作 | 执行耗时、写回与 ready 时刻 |
| 消费 | 每条操作读取的具体版本 | 就绪等待、读取时机、端口及执行资源竞争 |
| 释放 | 消费者关系及必要的生命周期标记 | 最后使用、在途读取、保留或退休等回收条件 |

“最后一个消费者是谁”不等于“它完成的周期就是释放周期”。如果 SSM 还有其他回收条件，模型也要保留。capture 时解释器的串行执行顺序也不应直接成为所有指令的执行顺序；后端应按程序顺序约束、依赖和资源状态决定重叠执行。

### 当前模型的一个具体差异

本次检查发现，模型把同一 storage_id 的不同版本按固定位置更新处理：新版本等待旧读者完成，再替换旧容量。

对于普通、可独立分配的 Local 结果，这个规则过强。SSM 可以让旧版本占据一份空间供旧消费者读取，同时为新版本分配另一份空间。因此，需要同时检查前端添加的覆盖依赖与 TileReg 的替换逻辑，让普通 Local 版本独立管理；显式别名、固定位置或特殊原地语义另行处理。

这是已经发现的实现差异和后续修改方向，本次记录没有修改仿真代码，也没有完成生命周期逐项对照验证。

### 我可以把方案称为“比较安全”吗

我的判断是：**在普通 Local tile 的值身份和消费依赖这一层，用动态版本 trace 驱动调度仿真有充分依据。它不会仅因变量同名，或省略架构名字解析，就丢失不同结果之间的区别。**

要进一步说生命周期严格对应，需要满足以下条件：

1. 比较的是对应的动态操作序列。编译器若消除了操作、插入复制或 spill，需要在输入中反映这些差异。
2. 普通 Local 结果确实走独立分配路径。别名 move、内部累加器等特殊行为需要单独表示。
3. 后端采用对齐的分配、消费、释放规则和相关资源约束。物理字节容量、架构命名窗口、vtag 表项数量是不同限制。
4. 固定 trace 所代表的执行路径适用于比较场景；如果同步或数据结果会改变操作序列，不能直接沿用一条不适用的 trace。

因此，我愿意把结论表述为：**PTO trace 已经保留了普通 Local tile 生命周期仿真所需的值与消费关系，能够支持与 SSM 建立严格对应；接下来应对齐并验证后端管理规则，而不是为了名字解析重新实现整套编译与重命名流程。**

“能够建立严格对应”是方案层面的结论。“当前周期、峰值容量和释放时刻已经一致”则需要用相同负载逐项验证，不能由版本身份一致直接推出。
